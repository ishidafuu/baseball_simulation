# 多人数ペナント（2部制・12球団）の設計

当初は7リーグ・42球団で設計し、保存の容量で2部制に縮めた（下記）。

⚠ **段階1〜3は実装済み**（参加者モデル・2部制12球団と昇降格・45分32ターンと
締め切り）。残りは段階4（場面別の采配）と段階5（ストーブリーグ）。
この文書は設計と実測の記録で、済んだ項目にも**なぜそう決めたか**を残している。

## 決まっていること

### 時間軸

| | |
|---|---|
| 1試合 | 45分ごと。1日32ターン（`TURN_MINUTES` / `TURNS_PER_DAY`） |
| 試合 | **月曜〜金曜の5日間＝160ターン（うち40は休養日、120試合）** |
| 土曜 | **ストーブリーグ**（契約更改・トライアウト・オフシーズン）32ターン |
| 日曜 | **キャンプ・編成** 32ターン |
| 月曜0時 | 新シーズン開幕 |

1週は 32×7＝224ターン。**シーズン1つ＝実時間1週間**。

⚠ **160は3連戦と6球団の総当たりの両方に割り切れる**。4ターンで1カード
（3試合＋休養1）なので40カード、1巡5節で8巡ちょうど、どの相手とも24試合・
本拠地12/12（全体で60ホーム・60ビジター）。実測で、144ターンだと
最後の1巡が途中で切れ「相手によって28試合と29試合」「ホームが71〜74」と
ばらついた。

⚠ **3試合に1回は休養日にする**（`REST_EVERY` = `CARD_GAMES` + 1）。
`recoverAllPitcherFatigue` は「その日出場した選手は回復させない」ので、
毎ターン試合があるとレギュラーの疲労が**一度も回復しない**。休養日に約-28（`体力×(0.25+回復/100*0.60)`）。
⚠ 下の表は一人用の溜まり方（1試合で約+11、`15 - 体力/100*8`）で測った頃の記録。いまオンラインの野手は
`onlineFielderGameFatigue`（`src/online/shared.js`）で溜まる: **3打席以上**（四死球・犠打を含む）出た日だけ、
体力80→+12・50→+15・20→+27（50を境に折る。先方指摘 2026-11-15）。実測は `online-fatigue-check`。

5試合に1休では1巡ごとに+27の積み残しになり、1シーズン通した実測で：

| 休養 | 全球団を休ませる | 終盤のレギュラー疲労 | 野手最大 | 打率 | 本塁打率 |
|---|---|---|---|---|---|
| 5試合→1休 | しない | 190 | 829 | .237→.189 | 0.58→0.28 |
| 3試合→1休 | しない | 66 | 877 | .238→.224 | 0.63→0.51 |
| 5試合→1休 | する | 60 | 220 | .239→.226 | 0.60→0.42 |
| **3試合→1休** | **する** | **15** | **80** | .241→**.237** | 0.58→**0.58** |

**両方そろって初めて平らになる**（`server/dailyLineup.mjs` の
`restTiredFielders` を全球団に当てること。詳細はそのファイルの注記）。

⚠ **球団の格付けを当て直すこと**。`ensureUserIndependentLeagueTagged` は
プリセット定義と**名前で**照合するので、その場で作った球団名は全部 'D'（最弱）に
なる。トライアウトの候補の質はこの格付けで決まるため、リーグ全体の選手が
弱くなっていた（実測でミート43.9→36.8、制球44.5→36.6）。

### 一人用との突き合わせ（20試合・12球団・同じ初期メンバーセット）

| | 一人用 | オンライン |
|---|---|---|
| 打率 | .229 | .232 |
| 1試合あたり本塁打 | 0.43 | 0.46 |
| 防御率 | 2.95 | 2.85 |
| 三振率 | 22.2% | 21.1% |
| 野手の疲労（平均） | 21 | 35 |

⚠ **疲労の最大値だけまだ開いている**（76 対 229）。出ずっぱりの数人が
休養日の回復量を上回って積み上げている。平均と集計値は揃っているので
当面は許容するが、休養の間隔（`REST_EVERY`）か代役の出し方で詰める余地がある。

⚠ **人の球団は特に積み上がる**。CPUは毎試合疲労を見て打順を組み直すが、人の球団は
保存した打順のまま出続けるので、ブラウザでの実測で遊撃手の疲労が8月に396まで達し、
打撃がほぼ0になった。いまは疲労80以上（自動采配の「疲れた野手を休ませる目安」`restLine` で早め60・遅め100にも。`restFatigueOf`）の野手を、その日だけ元気な控え（疲労40未満）と
入れ替えて休ませる（`server/dailyLineup.mjs`、中身は `src/online/restPlan.js` の `planRest`）。
守備はまとめて組み直し、ほかの先発が守備を移ることもある（二塁手を遊撃へ回し、控えの二塁手を
入れて遊撃手を休ませる）。どの守備も適性60以上で組めなければ休ませない。疲労120以上の野手は
組めなくても休ませ、守備の穴をいちばん小さくする（疲れの抜けていない控えも使う）。
その日に先発投手として抜ける二刀流の選手は、残る先発に数えない。保存した打順は変えない。

### この突き合わせは検査になっている（`online-parity-check`）

同じ球団数・同じ試合数・**同じ初期メンバーセット**で両方を動かし、打率・本塁打率・
防御率・疲労・能力・名簿の構成を並べて許容幅に収まるか見る。上の3つの不具合は、
どれも**個々の部品の検査はすべてPASSしたまま**すり抜けていた。試合の処理は
正しく、**世界の作り方**が違っていたため。

⚠ **比較で捕まるのは「オンラインと一人用の食い違い」だけ**。両方が同じ
エンジンを使うので、**共通の退行は比較では捕まらない**（両方が同じだけ壊れる）。
実際に「野手が疲労回復しない」を故意に入れたら素通りした。初期メンバーセットの
格の段差を壊して全体を弱くしたときも素通りした（一人用側も同じセットから組むので
両方が同じだけ下がる）。そのため、日程に休養日があることや格付けが一致すること、
セットの能力の水準（`online-pack-check`）は**別の検査**で数字を押さえている。

⚠ **名簿の作り方を変えたら、一人用側の組み方も合わせること**。オンラインを
初期編成からセット選択へ変えたとき、一人用側が初期編成のままで制球の平均が
48.2 対 54.2 とずれて落ちた。土台がずれていれば試合の処理が正しくても落ちる
（そして正しく落ちている——比較になっていないのだから）。

⚠ **比較の土台をオンライン側から取らないこと**。一度「一人用に渡す格付けを
オンラインの世界から読む」と書いたせいで、格付けが 'D' に落ちる不具合に対して
一人用側にも 'D' を渡してしまい、**間違いを基準にした比較**になって素通りした。
あるべき値（生成時の定義）と突き合わせること。

⚠ **操作IDに乱数を使わないこと**。進行の乱数は操作IDから作られるので
（`seeded(league, 'day:' + operationId)`）、毎回違うIDだと結果が揺れる
（実測で打率が .227〜.245）。固定すれば完全に再現する。

⚠ **平均だけ見ないこと**。12球団の平均は1球団が壊れてもほとんど動かない。
人の球団だけ野手9人（他は14人）でも平均13.6で埋もれた。最小・最大も見る。

1回およそ2分かかる。`npm run check` に入れてある。

⚠ **締め切りで自動決定する**。待ち続ける設計だと1人が決めないだけで
全員の週が止まる。締め切りを過ぎたら未提出の人に既定案（`defaultPhasePlan`）を
当てて先へ進む。

⚠ **締め切りが曜日合わせを兼ねている**。ストーブリーグは日曜0時、
キャンプは月曜0時が締め切りなので、全員が早く決めても次の開幕は
月曜0時まで来ない（曜日がずれない）。

⚠ **開幕前の手続きにも締め切りを置くこと**。以前は「最初の1回くらいは全員を
待とう」と設けなかったが、**1人が決めないだけでリーグが永久に止まった**
（実際に開幕前の日付のまま何日も動かなくなった）。時間による進行が絶対で、
決めていない人は標準案で押し通す。初期メンバー選択は土曜扱い（締め切り日曜0時）に
してあり、続くキャンプが月曜0時に締め切られて**月曜開幕**になる。

⚠ **手続きは1回の定期処理につき1つずつ解決する**。次の手続きの締め切りは
「開いた時刻」から数えるので、まとめて片付きはしない。止まらないことが大事で、
急いで進めることが目的ではない。

### 画面の分け方

左メニューは3つのまとまりに分ける。⚠ 以前は「今日/試合/選手/編成/手続き」が
平らに並ぶだけで、どこに何があるか辿れなかった。

| まとまり | 中身 |
|---|---|
| **情報** | チーム分析 / 球団史・記録 / リーグ史 / 試合結果 |
| **ロスター管理** | スタメン設定 / 投手起用 / 方針・采配 / 予告先発 / 指導者 |
| **手続き** | 現在の手続き / トレード / 練習試合 |

「チーム分析」と「リーグ史」は、いくつかの画面を1つのページにまとめ、見出しの下の切り替え
（`PageTabs`）で選ぶ（先方要望 2026-11-20）。チーム分析はチーム能力・成績 / スタメン・投手陣 /
守備分析 / 年齢構成 / 選手成績 / 通算成績、リーグ史は過去の順位 / プロ入りとその後 /
移籍・取引の記録 / 通算成績ランキング / 能力ランキング / 表彰・話題・オーナー。

スタメン設定と投手起用は、PC版では比べて決めるための1枚の表（`LineupBoard.jsx`・
`PitchingBoard.jsx`）。守備分析はスタメン設定の表に入れた。スマホ版の打順は2タップの表
（`TapLineup.jsx`）で、投手起用はPCと同じ表を全画面で開く（`MobilePitching.jsx`）。
（左メニューの正本は `DesktopView.jsx` の `NAV`）

⚠ 「自チーム情報」のページは**無くした**。所属・順位・勝敗は左メニューの
球団名の下に出し、名前の変更は左メニューの「名前を変える」から開く。
PCのページはどれも `Page`（見出し・補足・右に操作）で同じ枠に入れる。

⚠ **「方針・采配」は基本方針と自動采配だけ**にする。以前はここに
打順・守備／先発／投手の役割も区分切り替えで入っていて、移植した
「スタメン設定／投手起用／守備分析」と丸ごと被っていた（同じことを2か所で
設定でき、どちらが効くのか分からない）。項目が2つになったので区分の
切り替えも外した。携帯は左メニューを持たないので、「打順」のカードに打順と采配を
まとめて出す。PCは `DesktopTactics`、携帯は `LeaguePanels.jsx` の `LineupPanel`。
携帯の打順・守備・控えは2回のタップで入れ替える縦の表（`TapLineup.jsx`）で、
保存は方針・采配の下書きとまとめて1回送る。

⚠ **「能力ランキング」はリーグ全球団で並べる**（`abilityLeaders`）。
自球団の中だけだと、12球団288人の中での位置が分からず、自分の選手が強いのか
弱いのか判断できない。能力は元から公開の情報（他球団の名簿は「チーム分析」の「選手成績」から
能力も見られる）。並べ替えはサーバーで済ませる——画面は自球団の名簿しか
持っていないので、ここでは並べられない。

⚠ **移植画面は左メニューを覆わないこと**（`.online-lineup-portal` の `left`）。
全画面にしたら、スタメン設定から投手起用へ移れなくなった。

ホーム（既定の画面）に出すのは**3つだけ**。数字はすべてサーバーが作る
（`server/leagueBoard.mjs`）。画面で計算し直すと出どころが2つになる。

| | 左（広い） | 右（狭い） |
|---|---|---|
| 1 | 今後の6試合（自球団・先発予定つき） | リーグ順位（2部制） |
| 2 | 個人成績ランキング（打撃部門・投手部門） | |

- **今後の6試合** — 自球団のこれからの6試合（`ownUpcomingGames`）。
  **何試合目か**・ホーム／ビジター・両軍の先発予定を出す。
  ⚠ **日付ではなく試合数で出すこと**。1ターン＝ゲーム内1日で休養日が飛ぶので、
  「4/18」と言われても進み具合が読めない。番号は**消化済みも数える**
  （これから行う試合だけで1から振ると、シーズン中ずっと「1試合目」で始まる）。先発には**投げる手（右／左）と
  今季の勝敗・防御率**を添える（名前だけだと、どちらが有利な相手か判断できない）。
  ⚠ 投げる手は `physical.throws`。**選手直下ではない**ので、`player.throws` を
  見ると全員 `undefined` になり、既定に倒れて**全員が右投げ**として出る。
  ⚠ 投げていない投手の防御率は `null`（「防—」と出す）。0で割った値や 0.00 を
  出すと「無失点の好投手」に見える。
  ⚠ 先発の詳細は**ホームの一覧にだけ**重ねる。試合結果の画面が使う `upcoming`
  は名前しか出さないので、重ねると投影が重くなるだけ。
  ⚠ 6試合にしてあるのは、画面が2列×3行で**枠が埋まる**から（5だと1枠空く）。
  ⚠ 「今日」で絞らないこと（休養日や手続きの日に開くと空になる）。
  ⚠ ローテを回して出すこと（毎回同じだと1人が全試合に先発する予定になる）。
  予定であって確定ではない。
  ⚠ **日付順に並べ直すこと**。`pyramidSchedule` が作る配列は1球団ぶんを
  抜き出すとたまたま日付順になっているので、本物のリーグでは並べ直しを
  外しても気づけない（検査は作り物の日程で押さえている）。
  ⚠ リーグ全体の一覧（`upcoming`）は試合結果の画面が使うので、そちらを
  絞らないこと。
- **個人成績ランキング** — 打撃部門・投手部門に分けて各項目のベスト5。
  ⚠ 率の項目は**規定に届いた選手だけ**（混ぜると3打数2安打の控えが打率1位になる）。
  ⚠ 部門の分け方は**項目のid**で決める。並び順で切ると、項目を足したときに
  打撃と投球が入れ替わる。
- **2部制の順位表** — 勝敗に加えて**チーム打率・チーム防御率**を添える
  （`teamSeasonStats`）。
  ⚠ 選手の成績から足し上げること。順位表（`season.standings`）は勝敗しか
  持っていないので、別に数えた値を置くと選手成績と合わない数字が出る。
  ⚠ `inningsPitched` は**アウト数**。イニング数だと思って9を掛けると防御率が
  3倍になる。
  ⚠ 人が持つ球団には名前を括弧で添える。CPUには付けない。呼び名が球団名と
  同じときも付けない（参加時の既定が球団名なので「湘南サンズ（湘南サンズ）」と
  2回並ぶ）。
  ⚠ 列が7つになるので数字の列を詰める。既定の padding のままだと、
  自球団の行（持ち主の名前＋昇格圏の印が付く）だけ2行に折り返した。

⚠ **自球団は文字も黄色にする**（`.online-own-text`）。塗りだけだと12球団の表で
自分の行を目で追うことになる。順位表の行と、個人成績ランキングの自球団の選手、
今後の5試合の自球団側に当てる。一人用も同じ黄色で強調している。

⚠ **月間カレンダーは一度置いて外した**。12球団は全球団が毎試合日に試合をするので
1マスに6試合並び、自分に関係のある行を探すほうが手間だった。見たいのは
「次に誰とやるか」なので、自球団の6試合だけにした。
同じ理由で「今後の日程」（リーグ全体）もホームからは外している。
⚠ **リーグ便りはホームから外した**。「試合結果」の画面に残してある。

### 始める手順

**ログイン →（途中参加なら）参加する → セットを選ぶ → 球団名とプレイヤー名 → 決定**。

⚠ **参加の画面では名前を聞かない**。2か所で聞くと、どちらが効くのか分からない。
名前はセットの下で決める。

名前を決める欄は**初期メンバー選択の画面の、セットの下**に置く
（`PackSelect` の `TeamIdentity`）。`profile` 命令でその場で保存する。

⚠ **手続きの提出とは別の命令**にすること。セットの選択は締め切りで標準案に
上書きされうるが、名前は自分で付けたものなので上書きされては困る。

⚠ **入力中にビューが更新されても打ちかけを消さない**。45分ごとの進行や他の
参加者の操作でビューは何度も差し替わる。保存済みの値を取り込むのは
「まだ触っていないとき」だけにする。

⚠ **親が `view` / `run` / `command` を渡し忘れると、欄が黙って消える**
（画面は操作できたまま、名前だけ付けられない）。部品だけ描いても親の
渡し忘れは写らないので、検査は呼び出し元の字面でも押さえている。

⚠ 球団名とプレイヤー名は「自チーム情報」から**後からも変えられる**。
以前は参加のときしか付けられず、リーグを作った管理者には機会すら無かった。

### 途中参加した人も、自分のセットを選ぶ

開幕後に参加した人は、**2部の最弱CPU球団を引き継いだうえで、自分のセットを選ぶ**。
選んだ24人が名簿に入るのは**次の日曜のキャンプ**。それまでは引き継いだ選手で
CPUが戦う。

⚠ **シーズン途中で名簿を入れ替えないこと**。順位表と選手成績が合わなくなる。
キャンプは新シーズンの直前なので、そこで入れ替えれば勝敗は0から始まる。
待ち時間は最長でも5日ほど（シーズンが月〜金の1週間なので）。

⚠ **セットを保存に持たないこと**。20セット×24人＝480人を人数ぶん抱えることになる。
参加者には**種（`packSeed`）だけ**を持たせ、見るたびに `generateRosterPacks` で
作り直す（シードから決まるので何度作っても同じ選手になる）。

⚠ **種は人ごとにずらすこと**。セットの選手idは `種×1000＋1〜480` なので、
同じ種を使うと**別の球団に同じidの選手**ができて、記録がどちらのものか
分からなくなる（1セットは480人ぶんの幅に収まるので、種を1ずつずらせば重ならない）。

⚠ **キャンプの練習より後に入れ替えること**。先に入れ替えると、選んだばかりの
24人がキャンプで成長してしまい、セットの釣り合いが崩れる。

⚠ **決めなかった人には1つ目のセット**を渡す。空の名簿で開幕させない。

⚠ 済んだら `packSeed` と `pendingPackId` を消すこと。残ると毎キャンプで
名簿が作り直される。

### キャンプは4クールを自分で回す

一人用のキャンプ画面と同じ作りにする（`src/online/CampPlanner.jsx`）。
育成方針（長所／全体／短所 × 基礎体力／技術）で一括してから、選手ごとに
**メイン練習とサブ練習**を選び、「第Nクール練習を実行」を押す。
**全4クール**を、伸びた能力を見ながら1つずつ回す。終わったら、その能力で
スタメンと投手起用を整えて月曜の開幕を待つ。

⚠ **1クールずつサーバーで実行する**（`campRound` 命令 → `runCampRound`）。
画面で計算してまとめて送る形にしないこと——成長の計算は保存の正本に当てるもので、
画面で回すと手元の数字と保存がずれる。

⚠ **同じクールを2回走らせない**。押し直しや再送で成長が二重に積まれるので、
クール番号を送らせて、サーバーが**次の1つだけ**を受け付ける。

⚠ **自分で回したクールを数えること**（`phase.camp[userId].rounds`）。
数えないと、画面で4回やった球団が締め切りでもう4回やって**8クールぶん**成長する。
締め切りで回すのは「残り」だけ。CPUは4クールとも自動。

⚠ 4クール終えた人は**決定済み**として扱う。全員が終われば締め切りを待たずに次へ進む
（手続きの仕組みをそのまま使う）。キャンプには「この内容で決定」のボタンを出さない
——提出して待つものが無いので、出すと何を押せば進むのか分からなくなる。

サブ練習は13種（基礎体力・ウエイト・ストレッチ・守備補強・遠投・選球眼練習・
Cリード学習・変化球練習・新球種習得・スピン解析・サブポジ練習・フォーム改造・打席変更）。
表は `shared.js` の `CAMP_SUB_MENUS`。

⚠ **効かないサブ練習は出さない**（`subMenuFitsPlayer`）。変化球練習・新球種習得・
スピン解析は投手だけ、Cリード学習は捕手だけ。出すと、選べるのに
`executeSubTraining` が何もせず**そのクールが丸ごと無駄になる**。
入口（`validateCampRound` と `validatePhasePlan`）の**両方**で断ること——
片方だけだと、締め切りで回るぶんに効かない練習が混ざる。

⚠ **対象を選べるサブ練習は5つ**（`CAMP_SUB_TARGETS`。提出の `subTarget`）:
新球種習得（覚えたい球種）・変化球練習（磨きたい持ち球）・サブポジ練習（守備位置）・
フォーム改造（変えたいフォーム。**投手だけ**）・打席変更（変えたい打席。右・左・両）。
新球種・変化球・サブポジは「おまかせ」を残す（指定が無ければ中で選ぶ）。指定しても成功率は上がらない。
⚠ **フォーム改造と打席変更は「おまかせ」を出さない**（`CAMP_TARGET_REQUIRED`）。
対象を選んでいない・いまの形と同じ・もう変わったあとは、サーバーが**基礎体力**で回す
（`campSubKey`。`validateCampRound` の後、`runCampRound` で読む）。一人用は選ばなければ
中で抽選するが、オンラインは4クールを同じ指示で回すので、抽選だとクールごとにフォームが
変わり続ける。画面の選択肢も**いまの形を除く**（「サイドへ」「両打へ」。`subTargetChoices`、
アプリは `Commands.kt`）ので、変わったあとは「未選択」に戻る。打席の短縮名（右打・左打・両打）は
`constants.js` の `BATS_SHORT` が正本で、アプリの写しは `gen-tables.mjs` が書き出す。
⚠ 変化球練習の対象は**その選手の持ち球**で照らす（`validateCampRound` /
`validatePhasePlan`）。球種の一覧（`CAMP_PITCH_TYPES`）で照らすと、スプリットなど
持っていない形の球を選べてしまい、実行で「練習の対象が不正です」と弾かれていた。
極めた球種（100）は画面の選択肢から外す（伸びる余地が無い）。
⚠ 人の球団は、サブポジ練習のあとも**自分で決めた守備位置を保つ**。練習の中の
`syncPositionToFitness` は一番適性の高い位置へ戻すので、コンバートした選手が
サブポジ練習で元の位置に戻っていた（捕手が0人になることもあった）。CPU球団は従来どおり。
⚠ メインの新球種習得（球種）は入れていない（オンラインのエンジンが動かさない）。

⚠ **画面が出すメニューは、サーバーが受け取れるものだけ**（`CAMP_MENUS` /
`CAMP_SUB_MENUS`）。`TRAINING_MENUS` にはオンラインのエンジンが動かさないもの
（メインの新球種習得）があり、実測で画面に出ていた——選べるのに実行で弾かれる。
表は `src/online/shared.js` に置いて、サーバーと画面が同じものを見る。

⚠ **育成方針はやる気に効く**（`moodMultiplier`）。本人の希望と噛み合うほど練習が
身につく。希望どおりが正解ではない——噛み合いは効率にだけ効く。

⚠ **一人用の画面（`CampScreen`）をそのまま持ち込まないこと**。あちらは派遣・
大学リーグの昇降格・スタッフ退職まで抱えていて、オンラインのエンジンはそれらを
動かさない。出すと「できるように見えて何も起きない」ものが並ぶ。

⚠ **4クール終えたら `submitPhase` で提出すること**。印（`submissions[...].ready`）を
直に立てても**誰も解決しない**——手続きを解決するのは `submitPhase` の中
（最後の1人が決定した瞬間）だから。実測で、4クール終えてもキャンプが終わらず、
日付が1月1日のまま止まっていた。

⚠ **PCのキャンプは「ホーム」のページにカードで広く出す**（`DesktopView.jsx` の
`online-camp-card`。手続きのページの狭い枠に入れない）。能力表は23列あり、
740pxだと**メイン練習の選択すら見えない**（実測で表1100pxに対し見えていたのは694px）。
変化球の列は幅を止める——止めないと表が横に伸びて右端の列が隠れる。

⚠ **指導者の案を下書きにする**。任せ方が「意見を聞く」「任せる」のとき、コーチの案
（`campPlanFor`）をビューの `phase.camp.suggested` に載せ、画面はまだ保存の無い人に
それを初めの値として出す（PC・スマホ・アプリ）。締め切りで回る残りのクールも同じ案で回る
（`defaultPhasePlan`）。コーチの居ない側の選手・何もしなかった人は「おすすめ」で練習する。

⚠ **行を詰めること**。共通の `.online select` / `.online button` は指で押せる
大きさ（`min-height: 44px`）を持っており、そのままだと1行55pxで24人＝縦1900px超に
なる。表は目で追うものなので、中では外す（実測で31pxまで下がった）。
⚠ **守備位置のタブで1グループずつ出す**（投手／捕手／内野手／外野手。一人用と同じ）。
全員を並べると1行31pxでも1300pxを超え、下の実行ボタンまで何度もスクロールすることに
なる（実測で全部1326px → 1グループ928px）。

⚠ **携帯でも4クール回せるようにする**。表は23列あって携帯には入らないので、
育成方針と実行ボタンだけを出す（`compact`）。出さないと、携帯だけの人は
4クールとも自動になる。

⚠ **検査で `openPhase` を種の外で呼ばないこと**。トライアウトの候補は
`generateTryoutCandidates` が `Math.random` で作る。本物の進行は `advanceOneDay` が
`seeded(...)` の中で呼ぶので再現するが、検査が直に呼ぶと毎回違う候補になり、
人数や構成を見る判定が**ときどき**落ちる（実測で、同じコードのまま通ったり
落ちたりした）。

### 年間表彰（部ごとの MVP・新人王・ベストナイン・最優秀バッテリー）

タイトル8つ（首位打者〜最多セーブ）はリーグ全体のまま、こちらは**部（1部・2部）ごと**に選ぶ
（`server/seasonAwards.mjs` の `selectHonors`。成績を確定した10月下旬に `processSeasonEnd` の後で呼ぶ）。
成績から決めるだけで乱数を引かず、能力にもご褒美にも効かない（飾りと記録）。

- MVP: 規定（打席・投球回。10セーブでも可）に届いた人の中で値打ちが一番。部の1位の球団の人に少し足す。
- 新人王: **どの年も「22歳以下」かつ「このリーグの去年までの記録に出ていない」**（`isRookie`）。
  1年目は去年の記録が無いので年齢だけで決まる。規定の半分は出た人（`halfQualified`）。
  ⚠ 選手ごとの「このリーグに来た年」は全員には無い（1年目の CPU 球団の名簿には経歴が付かない）
  ので記録で見る。名簿にいて出なかった若手は翌年も候補のままだが、23歳で外れる。
- ベストナイン: 登録の守備位置ごと（外野は3人。DH は無い）。野手は規定打席の半分から。
- 最優秀バッテリー: 同じ球団の投手と捕手の組で規定投球回の半分以上を組んだ中で防御率が一番
  （捕手の記録 `records.seasons[年].players[鍵].catching.pitchers`）。⚠ いまの球団は**名簿**で見る
  （記録の `teams` は来た順に足すだけなので、A→B→A と戻っても [A, B] のまま）。
- ⚠ **部は表彰の時点で居る球団で決め、成績はその年の通し**。年の途中にトレードで部をまたいだ
  選手は、移った先の部で、前の球団の分も含めた1年分の成績で比べる（前の部では候補にならない）。

保存とビュー:

- 保存: `season.frozenAwards.honors`（部の id → `{ mvp, rookie, bestNine[], battery }`）。
  年度更新で `league.history[].awards` に写るので `history[].awards.honors` にも残る。
- ビュー: `chronicle.honors`（`honorsView`。いちばん新しい年のタイトルと部ごとの表彰。
  `{ year, titles[], leagues[{ league, mvp, rookie, bestNine[], battery }] }`）。表彰を足す前の年は
  `leagues` が空で、タイトルだけ。球団史の年表にも出す（`honorTitlesOf`）。
- 文はPC・スマホWeb（`chronicleText.js` の `honorRows`）とアプリ（`Chronicle.kt` の `honorRows`）で同じ。

### プロへ行った選手のその後

リーグからプロに指名された選手（`chronicle.proDrafted`）の、プロでの1年ごとの歩み
（`server/proCareer.mjs`）。**保存しない**飾りで、リーグの種・選手の鍵・年だけで毎回同じ答えを作る
（見る時期で過去の年が書き換わらない）。指名の翌年の10月（`PRO_SEASON_END_MONTH`）から1年ずつ出る。

- ビュー: `chronicle.proDrafted[].after`（いちばん新しい年の一行）、球団の窓口の球団史の
  `proDrafted[].career`（全部の年、古い順）、`chronicle.proNews`（今年の便り。10月から年度更新まで、
  目立った出来事のある人を先に3人まで。`{ name, team, npbTeam, text, highlight }`。引退・戦力外は
  `highlight: 'ended'`）。行ごとのその後は1回だけ作り、一覧と便りで使い回す（`proCareersOf`）。

### 年齢構成と3年後の見込み

自球団の年齢の段（投手・野手）と、主力の3年後の見込み（`src/online/ageOutlook.js`。成長力と
プロ意識から決まるピーク年齢で見る。乱数なし）。成長力を使うので**自球団だけ**作る。

- ビュー: `ageOutlook`（`{ years, bands[], grid[], core[], rising[], lines[], advice }`）。`grid[]` は「年齢 × 守備位置」の図の
  1人1つの箱（`id, name, position, group, age, later, core, warn`）。無い古いサーバーではアプリは前の帯の図に戻る。名簿が空のときと、
  **途中参加で初期メンバーを待っている間**（`packSeed`）は `null`（名簿は CPU のときの選手で、次の
  キャンプで入れ替わるため）。画面は `null` なら出さない（アプリの「年齢」の面は「まだ見込みを出せません」）。
- 出す場所: PC は選手成績（自球団を見ているとき）と手続きのトライアウト・契約更改（`compact`）。
  スマホWeb は手続きのトライアウト・契約更改（`compact`）。アプリは選手の「年齢」と、手続きの
  トライアウト・契約更改（`compact`）。

### はじめての1週間

途中参加した人に、参加してから7日の間だけ「スタメン → 投手の役割 → 方針 → 任せ方」の案内を出す
（`src/online/firstWeek.js`、アプリは `FirstWeek.kt`）。済んだか・閉じたかは端末に残す
（PC・スマホは localStorage、アプリは `SessionStore`。鍵は球団と参加の時刻）。

- 保存: `members[].joinedAt`（参加の手続きが入れる。リーグを作ったときの人には無い）。
- ビュー: `joinedAt`（無ければ案内を出さない）。

### 版（`ONLINE_SCHEMA`）を上げていない理由

上の4つで保存に足したのは `season.frozenAwards.honors`（と、その写しの `history[].awards.honors`）と
`members[].joinedAt` だけで、どれも**項目を足すだけ・無ければ空として読む**（表彰が無い年は
タイトルだけ、参加の時刻が無ければ案内なし）。プロのその後と年齢構成は保存しない。
なので `ONLINE_SCHEMA` は上げず、`MIGRATIONS` にも段を足していない。CLAUDE.md の「保存の形を
変えたら版を上げる」の例外で、`chronicle.proDrafted`（プロ指名）と同じ扱い。形を変える・
読み方を変えるときは版を上げること。

### 進行はターンで出す（ゲーム内の日付を出さない）

オンラインは**ターンで進む**（1ターン＝実時間45分＝ゲーム内1日）。画面には
ターンを出し、ゲーム内の日付（2024/4/18 など）は**出さない**。

⚠ ゲーム内の日付は進行の副産物でしかない。出すと「4/18って何試合目？」と
数え直すことになる。開幕（4/1）が第1ターン、最終が第160ターン（`SEASON_TURNS`）
（`turnOfDate` / `turnLabel` / `formatTurn`）。

⚠ **一覧では総数（/160）を出さない**。6試合ぶん並ぶと同じ数字が6回出る。
見出しだけ「第23ターン / 160」、一覧は「第23ターン」。

⚠ **実時間の締め切りは別もの**（`formatDeadline`・「次の進行」）。こちらは
消さない——次にいつ進むかが分からなくなる。

⚠ 範囲の外（開幕前・シーズン後）は `null`。文面を「開幕前」「シーズン終了」に
変える。数字のまま出すと、手続き中に「第225ターン」のような表示になる。

⚠ 「何試合目か」は球団ごとに違う（休養日があり、160ターンで120試合）。
試合の予定は別に数える（`ownUpcomingGames` の `number`）。

### 選手の枠は上限28人・標準26人（一人用は24人のまま）

⚠ **一人用の `ROSTER_TARGETS`（24人）とは別の表を持つ**（`ONLINE_ROSTER_TARGETS`
＝投手11・捕手2・内野6・外野7）。一人用の名簿と試合の釣り合いは24人で測って
あり、そこを動かすとドラフト・トライアウト・戦力外の釣り合いが全部ずれる。

⚠ **上限（`ROSTER_LIMIT`）は28人、標準（`ROSTER_STANDARD`＝目標構成の合計）は26人**
（先方要望 2026-11-16: 複数人のトレードができるように）。自動で埋めるのは標準まで
（`autoRosterTarget`: 人の球団は26人、CPU球団はリーグの種×年×球団のハッシュで26か27人）。
人の球団の27・28人目は、トライアウトで獲得する人数（`total`）を自分で決めたときと、
トレードで増えたときだけ。

⚠ **巡目は枠の数から取る**（`generateSnakeDraftOrder(names, ROSTER_LIMIT)`）。
直に 24 と書くと、枠を増やしたときに取り残され、名簿が空に近い球団が24人で止まる。

⚠ 人数は目標構成では決まらない。`selectPlayerForAI` は目標を「どの守備位置を
優先するか」にしか使わず、尽きても別の選手を取る。CPUにオンラインの表を渡して
いるのは**顔ぶれの偏りを揃えるため**。

⚠ 初期メンバーセットは**24人のまま**（2枠が空く）。空きは最初のトライアウトか
トレードで埋める。セットの構成と格の内訳の型を作り直さずに済む。

⚠ 検査の前提に**候補の数の余裕**を見ること。年末のトライアウトの候補は12球団で
実測120人。12球団×空き枠がちょうど120だと、必要な守備位置が先に尽きて1人埋まら
ない球団が出る（枠を26にしたときに実際そうなった）。

### 選手の詳細は1画面

選手名を押して出る詳細は、**タブで分けない**。
上から **札（守備位置・年齢・背番号・利き手・体格・出身）と経歴** →
**成績** → **能力** の順に、一度に出す（`PlayerDetailBody`）。

⚠ 以前は「成績／能力・人物／場面別」の3タブ＋その中でさらに区分の切り替えが
あり、1人を見るのに何度も押していた。

⚠ **縦に送らせない**。能力は列を増やして横に並べる（実測で高さ682px、
PCの画面に収まる）。項目を足すときは、どれかを削るか列を増やすかを考える。

⚠ **場面別だけは任意で開く**。打者×投手の組み合わせで行数が多く、1画面には
入らない。上の3つは常に見える。

⚠ 経歴は**新しい順**。古い順だと「いま何処か」が末尾になって読みにくい。
年の無い経歴（高校・大学）があるので `undefined年` と出さないこと。

### トレード

**提案 → 相手が「受ける／逆提案／断る」**。受ければその場で選手が入れ替わる。
逆提案は**提案した側に戻り**、そこで受ければ成立、断れば消える。

⚠ **逆提案は1回だけ**（`canCounter`）。何度でも投げ返せると終わらない。
2回目の返事は「受ける」か「断る」だけ。

⚠ **手番を持っている側だけが返事できる**（`canRespond`）。両方が同時に受けられると
二重に成立して、同じ選手が2球団に現れる。

⚠ **成立のときに中身をもう一度確かめる**（`assertTradeAllowed` を受けるときにも呼ぶ）。
提案から返事までの間に、その選手が別のトレードで移っていることがある。提案のときに
見ただけだと、居ない選手を動かして名簿が壊れる。

⚠ **両球団の名簿を見る**。自分の側だけ見ていると、相手の捕手を全部もらうような
提案が通る。条件はトライアウトの解決と**同じ**（投手1人・捕手1人・野手8人以上、
上限 `ROSTER_LIMIT`）——ここだけ緩めると、トレードで捕手のいない球団を作れてしまう。

⚠ **打順と投手起用を組み直す**（`refreshTeamPlan`）。出した選手が打順に残ると
試合が組めない。控えの投手を出しただけでは打順が変わらないので、検査は
**打順に入っている野手**で確かめること。

⚠ **相手はCPU球団でもよい**。CPU球団はその場で答える（受ける・逆提案・断る。
`src/online/trades.js` の `cpuTradeDecision`）。値段は画面の見込みメーターと同じ関数
（`server/tradeJudge.mjs`）で付け、値段が釣り合っても、提案した側ばかり戦力が上がる交換
（開きが `STRENGTH_GAP_LIMIT` 点を超える）は断る。CPUの逆提案は、受けるときに
いまの名簿でもう一度判断する（取っておいて名簿を変えてから受ける抜け道を塞ぐ）。

⚠ **相手がCPU球団なら、相手の考えていることを画面に出す**（`ThoughtsPanel`、式は
`src/online/tradeThoughts.js`。いしだ 2026-11-13「外野が欲しいのに内野を提案されたり。
相手の考えていることを表示するのはどうでしょう」）。出すのは**CPUが実際に使っている値**だけ:
弱い持ち場（持ち場ごとの一番手の力をリーグで順位づけ。ここを埋める選手をもらうと
`tradeStrengthGap` が縮むので通りやすい）、出しやすい選手の数（`needOf` が等倍＝上乗せが
乗らない人数）、出し渋る括り（上乗せが乗る）。⚠ **「弱い持ち場の選手を高く買う」と書かない**
（CPUはもらう選手に事情の上乗せを掛けない）。⚠ **人数を目標構成と比べて「足りない」と
言わない**（初期セットは外野が目標より少なく、12球団すべてが「外野が足りない」になる）。
食い違いは `online-trade-check` の③''（画面の値とCPUの `needOf` を突き合わせる）で止める。

⚠ **提案の数に上限**（`MAX_OPEN_TRADES`）。無制限だと相手の画面を埋められる。

⚠ **提案・逆提案には「ひとこと」を添えられる**（`TRADE_NOTE_MAX` 字。長すぎれば切らずに断る）。

⚠ **成り立たなくなった提案は自動で取り下げる**（`server/social.mjs` の `pruneTrades`）。出す・もらう
選手が名簿に居なくなった（別のトレード・退団・トライアウトの入れ替え）か、どちらかの人が参加者で
なくなったとき。当事者には「あなたへのお知らせ」で知らせる。**年度更新では全部取り下げる**。
人どうしの提案には時間の期限は付けていない（CPUからの提案だけ7日。下の「CPU球団のトレード」）。

**CPU球団のトレード**（`runCpuTrades`、`server/cpuTrades.mjs`）。シーズン中（7月まで）の1日の終わりに、
- **CPU同士の交換**: 平均 `CPU_TRADE_EVERY` 日に1回、1組。受ける側の判断は人の提案と同じ `cpuDecisionFor`。
  取引の記録に「CPU球団どうし」（`cpuOnly`）として残る。
- **CPUから人の球団への提案**: 球団ごとに平均 `CPU_OFFER_EVERY` 日に1回、未返事のものは1件まで。
  中身は「人が同じ交換を出したらCPUが受ける」もののうち、**人の側から見ても釣り合うもの**だけ
  （`planCpuTrade` の `balanced`・`fair`）:
  - 戦力の開きを**両向き**に見る（CPUばかり伸びる案も、人ばかり伸びる案も出さない）。人の弱い持ち場を
    埋めるCPUの選手も出す候補に入れ、両方の伸びの合計が大きい案を選ぶ。
  - **人の伸びが負の案は出さない**（`squadStrength` で人の戦力が下がる案。0 は可）。
  - 値段の下限: CPUが出す選手の値段が、人が手放す選手の値段（人の球団の事情こみ）の
    `CPU_OFFER_VALUE_FLOOR`（0.85）倍以上。
  - 案の無いCPUが多いので、その日のくじが当たったら**その日の順に全CPUを見て**、最初に案が見つかった
    球団が言い出す。
  - 人の同じ選手を続けて求めない: ある人の選手を求める提案を出したら、**どのCPUからも**
    `CPU_OFFER_MEMO_DAYS`（30）日はその選手を求めない（断っても、期限で取り下げられても、受けても）。
    覚えは `league.cpuOfferMemo`（`{ team: 人の球団, id: 求めた選手, until: この日付キーより前は求めない }`、
    新しい順。期限の過ぎたものは次に書くときに捨て、件数は `CPU_OFFER_MEMO_MAX`（200）まで）。
    足すだけの項目なので版は上げていない（無ければ空とみなす）。前の形 `league.cpuOfferLog`
    （「球団>選手id」の文字列、全球団共用の30件。同じCPUだけを避けたので、別のCPUなら人の同じ主力を
    続けて欲しがれた）は日付が無いので読まず、次に提案を出したときに消す（判断7、いしだ 2026-11-20）。
  **`CPU_OFFER_DAYS`（7）日の期限**があり、過ぎると取り下げてお知らせする。受けるときは、いまの名簿で
  もう一度CPUに判断させる。
- 人がCPUからの提案に**逆提案すると、CPUがその場で答える**（受ければ成立、応じなければ元の提案のまま残る）。
- 乱数は引かない（`dayRoll`。リーグの種×日付×用件のハッシュ）。同じ日をやり直せば同じ結果。
検査は `online-cpu-trade-check`。

⚠ 断るのは**どちらの側からでもできる**（提案した側は取り下げになる）。

⚠ **逆提案の画面で左右を入れ違えないこと**。`trade.offer` はいつも
「提案した側（`fromTeam`）が出す選手」なので、提案を**受けた側**から見ると
それは相手の選手。そのまま自分の欄の初期値にすると、相手の選手を自分が出す形で
送ってしまい「出す選手が名簿にいません」で断られる（実測で踏んだ）。

⚠ **途中参加でセットを待っている球団とはトレードしない**。名簿は次のキャンプで
丸ごと置き換わるので、受け取った選手が消え、出した選手だけ相手に残る。

⚠ **人の球団の救援の欄も名簿に合わせる**（`syncRelievers`）。先発ローテが揃って
いれば編成は残すが、出した救援投手を欄から外し、入ってきた投手を中継ぎに足す。
足さないと、もらった投手が試合で1度も投げない。

#### 画面（PC。`TradeScreen.jsx`）

トレードは「この交換で自分の球団は良くなるか」を**比べて決める**画面にする。

- 守備位置ごと（投手・捕手・内野手・外野手）に、**自球団と相手の選手を1枚の表**に
  並べる（スタメン設定と同じ考え方）。列がそろうので上下で見比べられる。
  列は総合・能力・今季成績（投手は変化球も）。自球団の行には起用の札（4番・先発2 など）。
- 行を押すと右の**交換案**に入る（自球団の行＝出す、相手の行＝もらう）。交換案には
  選んだ選手と、交換のあとの**両球団の人数と構成**（投・捕・内・外）を出す。
- 名簿が成り立たない交換は理由を出して提案できなくする。判定は**サーバーと同じ関数**
  （`rosterShortfall` / `rostersAfterTrade`）を使い、画面に別の式を書かない。
- 届いた提案・出した提案も、出す選手ともらう選手を同じ列の表で並べ、交換のあとの
  構成を出す。逆提案は元の中身を選んだ状態で同じ画面を開く。
- ⚠ 相手の名簿は読み直しの間も**前の名簿を出し続ける**。読み直すたびに空にすると、
  画面の更新のたびに相手の表が消えて、押そうとした行が無くなる。
- 検査は `npm run check:online:trade-ui`（dist を開く。サーバー不要）。

### 人どうしの関わり（版13）

数字は `src/online/social.js` にまとめ、サーバー・PC・アプリ（`Tables.kt`）が同じものを使う。
検査は `online-social-check`。

- **あなたへのお知らせ**（`member.inbox`、`INBOX_LIMIT` 件）。トレードの返事・取り下げ、練習試合の
  申し込み、予告先発を使えなかったこと、おかえりなさい など。文はサーバーで作って保存する
  （PC とアプリで同じ文を出すため）。
- **取引の記録**（`league.transactions`、`TRANSACTIONS_LIMIT` 件・およそ2年）。トレード・退団・入団を
  その時の選手名で残す。上限で古いものを落とすときも、球団ごとに新しい `TEAM_TRANSACTIONS_KEEP`（40）件は
  残す（球団史の入退団履歴のため）。
- **最終ログイン**（`member.lastSeenAt`）。見せ方は「今日・昨日・N日前」だけ（時刻は出さない）。
  書き直すのは `PRESENCE_REFRESH_HOURS` ごとか、日本時間の日付が替わったとき。⚠ ただの書き直しでは
  `revision` を上げない（送信中の提出を弾かない）。参加したとき・リーグを作ったときにも入れる
  （入れないと、その人は留守にならない）。
- **おるすばん**: `AWAY_DAYS` 日来ていない人の球団は、スタメン・投手起用・采配・手続きを指導者に
  任せた扱い（`effectiveStaffModes`）。⚠ 本人の任せ方の設定は書き換えない。留守になる前の編成を
  `member.awayPlan` に控え、来たら（`touchPresence`）任せていない分野だけ元に戻す（選手が動いて成り立た
  なければ指導者の案のまま）。解いたときは `revision` を上げ、`presence` の答えに `returned: true` を
  付ける（PC・アプリは読み直す）。控えは年度更新で消す。
- **留守中のまとめ**: 前に見たビュー（端末に残した分）と今のビューを比べて、勝敗・順位の動き・届いた
  お知らせを帯に出す（`awaySummary.js`、アプリは `AwaySummary.kt`）。部の順位は順位表と同じ並べ方。
- **回の攻撃**: 試合の箱の `plays`（`server/recordedStats.mjs` の `inningPlaysOf`、画面は
  `src/online/gamePlays.js`）。スコアボードの回の数字を押すと、その半回の行を順に出す。
  形は `{ '3t': [[打者の番号, 記号, 点, アウト], ...], '3b': [...] }`（鍵は回＋t 表／b 裏）。
  打者の番号は `teams[攻撃側]` の並びの番号、記号は 本/三/二/安/四/死/振/犠/併/失/凡 と、打者の
  居ない行の 走（打席の外や打席の途中に入った点）・刺（盗塁死など走者のアウト）。点はその行で
  入った点、アウトはその行で増えたアウト（試合のアウトそのもの。振り逃げ・野選は0）。
  ⚠ 半回の点の合計はスコアボードのその回の数字と合う（`online-inning-plays-check`）。
  ⚠ 2026-11-20 より前の試合の行は3要素（アウトが無い）で、画面は記号から数える。
  それより前（版16より前）の試合には `plays` 自体が無い。練習試合の箱には残さない
  （画面が読まないため。2026-11-20 監査で外した）。
  版20から、行の5つ目から `[塁, 守備位置, 向き, 飛距離, 角度]` を足した（新しい見た目の試作の打席速報。
  Web は `src/online/look/playByPlay.js`、アプリは共通部の `LookPlay.kt` が読む）。塁は**その行の後**の
  走者（一塁＝1・二塁＝2・三塁＝4 の和）、打球の4つは前へ飛んだ打席だけ、打席の外の行は塁だけ。
  1試合あたり約1.9KB。版19以前の試合は打席速報を出さない（`hasLivePlays`）。
- **得点経過**: 試合ごとの得点の場面（`scoringPlays`）。回の攻撃が無い前からある試合にだけ出す
  （PC は試合成績に、スマホWeb はリプレイがある試合は「試合経過」、無い試合は畳んだ「得点経過」で。
  小窓を縦に収めるため）。
- **予告先発**: 自球団の先の `STARTER_PICK_GAMES` 試合で先発を指名できる。試合の `STARTER_LOCK_TURNS`
  ターン前に確定し、そこで初めて相手にも見える（それまで相手の指名は見えない）。
  ⚠ **確定したときに見えていた先発を控える**（人の球団すべて。指名が無ければローテの次の投手。
  `member.lockedStarters`）。試合の日はその投手が投げる（ローテを組み替えても、おるすばんが
  付いたり外れたりしても変わらない。その日だけ差し込み、ローテの順は戻す）。名簿に居ない・登録外・
  疲労 `STARTER_SKIP_FATIGUE` 以上なら普段どおり選び、指名だったときは理由つきで知らせる。
  CPU球団は今までどおりローテの順。手続きの間・進行を止めている間は指名できない。
- **練習試合**: 人の球団どうしだけ。申し込み（ひとこと `CHALLENGE_NOTE_MAX` 字、出しておけるのは
  `MAX_OPEN_CHALLENGES` 件）→ 相手が受けるとその場で1試合。**同じ相手とは日本時間の1日に
  `EXHIBITIONS_PER_DAY` 試合まで**（相手が違えば同じ日に何試合でもできる）。2球団を写しに
  差し替えて行い、成績・疲労・調子を残さず世界も保存し直さない。結果は `EXHIBITION_LIMIT` 件残す
  （今日の分は消さない。1日の数え方に使うため）。手続きの間・進行を止めている間は申し込めず受けられ
  ない（断る・取り下げるはいつでも）。年度更新で申し込み中のものは取り下げる。
- **オーナーのひとこと**（`OWNER_COMMENT_MAX` 字）。順位表・球団の画面・紙面に出す。文が同じなら
  書いた日付を変えない（球団名だけ変えたときに「新しいひとこと」にならないように）。
- **参加者の管理**（管理者の `releaseMember`）。抜けた人の球団はCPUに戻し、申し込み・提案を取り下げる。
  ⚠ 次に入る人の種の通し番号は `memberSeq` だけでなく、残っている人の種と名簿の選手の id からも数える
  （版13へ上げた保存には `memberSeq` が無く、抜けたあとに入った人が既存の人と同じ選手 id になった）。

### 検証モード

作っている間は、45分ごとの進行を待っていると試せない。管理画面の**検証モード**をONに
すると、管理者だけ「手続きをいま締め切る」「1ターン進める」「24ターン進める」が
使える。⚠ **遊び始めたらOFFに戻すこと**（好きな時に進められるのは公平ではない）。
環境変数 `ONLINE_ALLOW_STEP` でも立つが、そちらは再デプロイが要る。

⚠ **1ターン＝実時間45分＝ゲーム内1日（＝1試合か休養日）**。「1日進める」と書くと
どちらの1日か分からないので、画面にはターン数とゲーム内の日数を併記する。

⚠ **以下の3つが揃って、はじめて週の割り当てが成り立つ**（2026-11 に直した。
それまでは1年に約240ターンかかり、曜日がずれていた）。

- **NPBドラフトは一人用の処理（`processNPBDraft`）を回さない**。一人用は各球団から2〜3人ずつ抜くので、
  長く続ける対人リーグでは育てた選手が手元から消えすぎる。代わりに**プロ野球への道**
  （`server/proDraft.mjs`、先方要望 2026-11-16 で解禁）で、**プロに達した能力の選手だけ**を
  若さ・能力・タイトルから選ぶ（`PRO_DRAFT_THRESHOLD`。枠は年5人まで、実測で年平均1.1人・0人の年が3割）。
  ⚠ **指名は確率ではない**（いしだ 2026-11-19）。線を越えた選手はその年に抜かれる（枠の5人を超えた分は点の低い方から翌年に回る）。厳しさの摘みは
  しきい値だけで、上限を上げても0人の年は減らない。タイトルの規定は本物のタイトル（`processSeasonEnd`）と同じ規定打席・規定投球回。
  抜かれた球団のチームメイトにプロ意識+5・経験+30試合分を渡し、`league.chronicle.proDrafted` に
  残す（球団史・リーグ記録・入退団履歴・リーグ便り）。乱数はリーグの種×年のハッシュ。検査は `online-pro-draft-check`。
  ⚠ **同じ日の「成績の確定」は残すこと**（比較値・タイトル・最終順位）。指名はその**後**に行う。
  ⚠ **育成評判（`developmentReputation`）はNPB輩出だけが上げていた**（一人用の処理）ので、
     オンラインでは0のまま動かない。トライアウトの受験者は基本の帯が中心で、高卒の一部は
     帯の外の逸材枠（プールの最上位から。人数はリーグの格で増える）と素材枠（一芸の強い選手）から来る。
- **シーズン後の空き日はまとめて進める**（`advanceLeagueDay`）。レギュラーシーズンは
  4/1〜9/7 の160ターンで終わるが、プレーオフは10/10、契約更改は11/9。この間を
  1ターンに1日ずつ進めると何十ターンもかかる。いまはレギュラーシーズンが
  終わったあとの「試合の無い日」を1回の進行で最大60日ぶん進める。
  ⚠ 日付を飛ばすのではなく**1日進行の繰り返し**（間の大会・手続きの判定を落とさない）。
  ⚠ レギュラーシーズン中の休養日はまとめない（1ターンとして数える設計）。
- **開幕は月曜0時**（`seasonStartAt`）。キャンプが早く決まっても次の月曜0時まで待つ。
  月曜に入ってから決まったとき（締め切りの自動決定を含む）は次の枠（45分刻み）から始める。
- **土曜の32ターンを3つで分け合う**（`PHASE_WINDOW_HOURS`）。締め切りは
  「担当曜日の0時＋持ち時間」で、契約更改=土12:00（16ターン）・
  トライアウト=土21:00（12ターン）・年度更新=日0:00（4ターン）。
  ⚠ 以前はどれも「翌日0時」だったので、契約更改が締め切りまでかかると続く
  トライアウトは日曜に開き、**キャンプの32ターンを食っていた**（実測で
  ストーブリーグ52ターン・キャンプ8ターン）。いまは 30 / 32。
  ⚠ 担当日の合計が24時間（32ターン）を超えないこと。
  ⚠ ここを動かすと**考える時間の長さ**が変わる。非同期で遊ぶゲームなので、
  短くしすぎると寝ている間に標準案で決まる。
- **年度更新は手続きとして待たない**（2026-11-08 いしだ指摘）。決めることが無いのに
  「この内容で決定」を押させていた。11/30 に開いたその場で済ませ（`openPhase` → `resolvePhase`）、
  続けてキャンプが開く。トライアウトの締め切り（土21時）の次の進行でキャンプが始まるので、
  キャンプは月曜0時まで約27時間ある。`PHASE_WINDOW_HOURS.offseason` は古い保存で
  年度更新が開いたままのリーグのために残している。
- **1年の流れの帯**（`SEASON_STEPS` / `seasonStage`、`src/online/SeasonFlow.jsx`）。
  サーバーがいまの段階をビュー（`stage`）に載せ、PC・スマホ・アプリが同じ7段階で描く。
  手続きの合間（契約更改→トライアウト、トライアウト→キャンプ）は「次の進行で〇〇が開きます」と出す。
- **年度更新の伸び・衰えを残す**（`offseasonChanges` → `league.offseasonResults` → ビューの
  `lastOffseason`）。能力が変わるのはキャンプと年度更新だけで、年度更新のほうは画面に何も
  出ていなかった。実測（1人リーグ1年）: シーズン中の変化はゼロ、年度更新は主な能力が+1程度。
  ⚠ **Web は 2026-11-18 から年度更新の伸びを出さない**（いしだ「キャンプの結果やオフの成長は要りません。
  その年の順位、入退団の選手、主なトピックに止めて下さい」）。代わりに**その年のまとめ**
  （`server/yearSummary.mjs` → ビューの `yearSummary`、画面は `YearSummary.jsx`）を、年度更新から
  **開幕した月の終わり**まで出す（`isYearSummaryTime`。キャンプの間だけだと約27時間しか無く、
  日曜に開かなかった人は見られなかった）。時期の外はビューに載せない。
  ⚠ **出す場所は 2026-11-22 に替えた**（いしだ「ホームのトップに表示されている『〇年目のまとめ』は、
  各チーム分析に入れて下さい」）。PC のホームの先頭からは外し、**チーム分析の「チーム能力・成績」**に
  置いた。球団を選べば他球団のまとめも見られるよう、`projectTeamInfo` にも `yearSummary` を載せている
  （順位はその球団の部・入退団はその球団の分）。キャンプの画面と手続きの画面には残してある。
  スマホは**チーム分析が無い**ので、ホームに出したまま。アプリも 2026-11-20 に
  同じまとめへ移した（`YearSummary.kt`・`YearSummaryCard`）。`lastOffseason` はアプリの通知
  （`year`・`departed`）がまだ読むので残している。能力の差（`gains`）は Web もアプリも読まなくなったが、
  古い版のアプリが空の札を出すだけなので、ほとんどの人が新しい版にしてから外す。
- **打撃フォーム**（オープン/スクエア/クローズ。`src/game/batterZone.js` の `BATTING_STANCES`）。
  いしだ 2026-11-23「オープン：インコースが得意になり、アウトコースが苦手になる／スクエア：平均的／
  クローズ：アウトコースが得意になり、インコースが苦手になる。また、体格によっても違いを出します
  （大柄：アウトコースが得意／普通：平均的／小柄：インコースが得意）…苦手を無くす打撃フォームにするか、
  得意を伸ばす打撃フォームにするか、プレイヤーの判断で変わります」。
  内外角の得手不得手（`inside`）に**フォーム±0.35・体格±0.20**を重ねる（先天の偏りのσは0.34）。
  同じ向きに積めば端へ寄り、逆向きなら打ち消せる。**体格が試合に効くのはこれが初めて**
  （それまでは生成時の能力と守備適性だけだった）。
  ⚠ 既定は**名前とIDから決まる**（スクエア50%/オープン25%/クローズ25%）。生成箇所が散在していて
  全部に足すと漏れる、というこのファイルの方針に合わせた。変えたときだけ `battingStance` が選手に載る
  （`ONLINE_SCHEMA` 20・移行は足す方向だけ）。
  ⚠ 変えるのは**キャンプの「フォーム改造」**。2026-11-23 から投手も野手も使える（投手は投球フォーム、
  野手は打撃フォーム）。対象の種類は `campTargetKind` が選手で分ける（サーバーの受け付け・実行・画面・
  アプリの4か所が必ずこれを通す）。判定は `batter-stance-check`。
- **NPBドラフトの発表**（Web の `ProDraftResult.jsx`・アプリの `ProDraftCard`。ホーム・手続き・契約更改）。
  中身はビューの `chronicle.proDrafted` のその年の行。名前を押すと指名した時点の能力が開く
  （保存の `proDrafted[].player`。`server/proDraft.mjs` の `draftSnapshot` で、新しい24件にだけ
  残す。ビューには今年の指名の分だけ載せる。`server/chronicle.mjs`）。
- **遅れて開いた手続きは短い猶予で締める**（`LATE_PHASE_GRACE_HOURS`）。持ち時間を
  過ぎてから開いたときに翌週まで待たせないための保険。通常は上の枠で収まる。
- **ストーブリーグが32ではなく30ターンなのは、プレーオフが土曜の頭を2ターン使うため**。
  レギュラーシーズンは金曜23:15に終わるが、プレーオフ（ゲーム内10/10〜10/12）と
  空き日のまとめ進みに実時間で2ターンかかる。週の合計（162+30+32=224）は合っている。

（履歴）1時間刻みだった頃の実測（2人・既定案・キャンプを火曜12時に決定）：月曜0時開幕 →
金曜22時にレギュラーシーズン終了 → 土曜1時に契約更改 → 日曜1時にトライアウト（13時締め）→
日曜14時にオフシーズン（18時締め）→ 日曜18時にキャンプ（月曜0時締め）。1年が124ターン＋手続き。
さらに前は「1枠進むと1日進む」で1日7枠だった。**いまの刻み（45分・160ターン・手続きの締め切り）は
上の箇条書きが正本**で、この段落は経緯として残している。

見出し（「NEXT STAGE」の右）にも、検証モードの間だけ2つ置く。

- **1日程進める** — 決定待ちの手続きがあれば**それを締め切り**、無ければ
  1ターン（ゲーム内1日・1試合）進める。
  ⚠ 手続き中は試合が進まないので、締め切りを兼ねないとボタンが効かない日が続く。
- **全データリセット** — リーグも成績もすべて消して、作成前に戻す（`reset`）。
  ⚠ **二度押しにすること**。押し間違いで全員の成績が消える。
  ⚠ **バックアップも一緒に消すこと**。残すと「リセットしたのに復元できる」
  状態になり、何が正本か分からなくなる。
  ⚠ 版の照合は飛ばす（壊れて読めなくなったリーグを捨てるための操作なので、
  版が合うことを前提にできない）。代わりに**「リーグが無い」を先に見る**
  ——`canStep(null)` は false なので、順を逆にすると2回目が
  「検証モードが入っていません」になって何が起きているか分からない。
- ⚠ どちらも**リーグがまだ無いときは画面に出さない**。押しても断られるだけで、
  リセット直後に押せるように見えるのが紛らわしい。


### リーグ構造（2部制・12球団）

```
   1部   （6球団）
   2部   （6球団）
```

| 階層 | 昇格 | 降格 |
|---|---|---|
| 1部 | — | **最下位** → 2部 |
| 2部 | **1位** → 1部 | — |

1つ降りて1つ上がるので**出入りが釣り合う**（検査が自動で確かめる）。

⚠ **7リーグ42球団は見送った。** 保存の容量が無料枠に収まらなかった（下記の実測）。
構造は `PYRAMID_LEAGUES` の表1つで決まるので、容量の目処が立てば広げられる。

⚠ **降格は「下から数える」こと**（`RELEGATION_FROM_BOTTOM`）。
「6位」と上から書くと、1リーグの球団数を変えたときに最下位でない球団が落ちる。

### 容量（実測）

毎ターン世界スナップショットを全部書き直す作りなので、
**記録が増えるほど1回の書き込みが重くなる**。

| 構成 | 球団 | 1シーズンの試合 | 月間書き込みの目安 |
|---|---|---|---|
| **2部制（採用）** | 12 | 864 | **約1.6 GB** |
| 3リーグ | 18 | 1,296 | 約2.4 GB |
| 4リーグ | 24 | 1,728 | 約3.2 GB |
| 7リーグ | 42 | 3,024 | 約5.5 GB |

⚠ 観戦リプレイ（1球ごとの記録）は**既定で保存しない**。
1試合218KBのうち182KB＝84%を占め、42球団では1シーズン670MBとなって
`JSON.stringify` の上限（約512MB）を超えた。成績だけなら1試合30KB。
球団数の少ないリーグで観戦したいときは `ONLINE_RECORD_REPLAY=1` で有効にできる。

**2部制の実測**: 1試合30KB / 1シーズン25MB / gzip後2.3MB。

⚠ **上の見積もりは試合結果の重複を数えていなかった**。2026-11 に1年通しで測ると、
契約更改の時点で保存が192MB（gzip 24MB）あった。試合結果に両球団の名簿の写し
（1試合約100KB）が入り、しかも `season.results` と `season.schedule[].result` の
2か所に入っていたため。いまは保存前に写しを外している（`slimStoredResults`。
個人成績は記録 `records` に別にある）。外したあとの実測は、2年目のキャンプ時点で
77MB（gzip 7.2MB）。残りの大半は世界の球団（CPU以外の約550球団、約47MB）と
記録（約22MB）で、ここを減らすのは今後の課題。

### 参加者

| | |
|---|---|
| 人数 | **1〜12人**。随時追加できる |
| 入口 | **アカウントを持っている人は誰でも**。アカウントは管理者が配る招待リンクから本人が作る |
| 残りの球団 | CPU |
| 途中参加 | **2部（最下層）から。CPU の最下位が弾かれる** |

⚠ **球団名は「表示名」で持つ**（`displayName`）。内部名（`name`）は
`TEAMS_DATA` のキー・日程の対戦相手・順位表・記録の選手キー（`onlinePlayerId`）
まで貫いているので変えられない。参加した人が付けた名前は、投影の `teamLabels`
（内部名 → `{ label 正式名, short 略称, base 枠の既定の略称, city 地域名, nickname チーム名, region 地方 }`。
作り方は `src/online/membership.js` の `teamDisplayOf`）で渡して画面だけ差し替える。
地域名・チーム名・地方は分けて付けた球団だけが持つ（`displayCity` / `displayNickname` /
`displayRegion`）。略称は地域名、`region` は選んだ地方だけ（選んでいなければ null で、
地元は今までどおり球団の土地の地名から引く）。CPUに戻す・別の人が入る・古い送り方
（`teamName` だけ）で名前を変えるときは、3つとも消す（古い送り方で、新しい名前が
いまの地域名で始まるときだけはチーム名を差し替えて地域名と地方を残す）。
これが無かったとき、名前を付けても画面には引き継いだCPU球団の名前が出ていた。

⚠ **略称はリーグの中で1つずつ**（判断1・2026-11-20 監査）。名前を変える（`profile`）・
参加する（`join`）ときに、新しい略称（地域名があればそれ、無ければ付けた名前の頭3文字、
付け替えていなければ枠の既定の略称）が次のどれかと同じなら 409 で断る。

- ほかの球団の**いまの**略称（1部・2部を問わず全球団。昇降格で球団は毎年リーグを移るので、
  同じリーグの中だけを見ると昇格した年に同じ略称が2つになる）
- ほかの枠の**既定の**略称（`abbreviation`。CPUに戻すと枠は既定の名前に戻るので、
  その略称を別の人が取っていると戻したときにぶつかる）

**いまの略称のままなら断らない**（既にぶつかっている保存データでも、名前を変えずに
ひとことだけ直すのは通す）。分けずに付け替えた古い球団の小窓は地域名が既定の都市で
埋まって開くので、正式名が変わらないかぎり名前は今の形のまま残す（略称が変わって断られ、
ひとことすら直せなくなるのを避ける）。判定は `src/online/shared.js` の `findShortClash`、
略称の作り方は `shortNameOf` の1か所で、サーバー（`membership.js`）と Web の小窓
（`DesktopView.jsx` の `RenameDialog`。保存の前に知らせる）が同じものを使う。
参加の画面はビューを持たないので、サーバーの 409 だけで知らせる。

⚠ **ここが最大の変更点。** 現行は参加者を Vercel の環境変数
（`ONLINE_MEMBER_1` / `ONLINE_MEMBER_2`）で決めており、
1人追加するたびに環境変数の編集と再デプロイが要る。42人には使えない。
`createLeague` にも `members.length === 2` の強制がある。

**参加者はリーグのデータ側で持つ**形に変える。環境変数に残すのは
「誰が管理者か」だけでよい。

⚠ `docs/online/README.md` に「**途中参加**は対象外」と書かれているとおり、
途中参加は未実装。今回これを実装する。

### 球団

**全球団（いまは12）ランダム生成**。プロ扱いで、独立リーグと同じ形式。

既存の `INDEPENDENT_LEAGUES` には **26球団**しかないので、
42球団を生成する仕組みを作る。人間が参加した球団は**本人が命名**して上書きする。

### 采配

**自動**。人は試合に立ち会わない（45分ごとに進むため）。
代わりに**場面ごとの方針**を事前に設定する。

土台は `src/online/tactics.js` にある。

- 打撃方針 / 投球方針 / 走塁方針 / 守備方針
- 先発の役割（完投型・勝ち権利型・ショートスターター・オープナー等）
- 中継ぎの役割（ロングリリーフ・セットアッパー・クローザー・ワンポイント等）
- 球数制限・ダメージ基準・バント/代打/守備固めの積極度

これを**条件付き**へ拡張する（「7回以降・1点差なら」「対左投手なら」など）。

### 指導者（監督・投手コーチ・野手コーチ）

全球団に3つの席を置き、その人の**ビジョン**（攻めの型 × 守りの型 × 時間軸、看板は攻めか守り）と
性格で球団ごとの野球の色を出す。計算は `src/online/coaches.js`（乱数を引かない関数と、種を決めて
引く生成）、リーグの保存の読み書き・人事は `server/coachEngine.mjs`、画面の文は `server/coachView.mjs`。
仕様書は `coaches.js` の冒頭にリンクがある。保存は版10で足し、ビジョンは版12で足した。

⚠ **監督・コーチは人の采配の肩代わり。能力や試合に上乗せしない**（オーナー決定 2026-11-10）。
型で強さを変えない。効くのは、人がいま選べる設定（采配・方針）と、CPUが使っている点数の重み
（トライアウト・退団・トレードの見る目、キャンプの方針）だけ。人が同じ設定を選べば同じ試合になる。

人の球団は分野ごとに任せ方を選ぶ（`STAFF_MODES`。保存は `member.staffModes`、無ければ既定）:

| 任せ方 | 何が起きるか |
|---|---|
| 自分で | 指導者を入れる前とまったく同じ動き（検査で確かめている） |
| 意見を聞く（既定） | 采配は「AI判断」の項目にだけ指導者の考えが入る。手続きは指導者の案が下書き・標準案になり、変えてから出せる |
| 任せる | 指導者が決める。手続きは**提出があっても指導者の案で決まる**（提出は「確認した」の印だけ）。スタメン・投手起用はCPUと同じく作り直す |

分野は スタメンと打順（野手コーチ）・投手起用（投手コーチ）・試合中の采配（項目ごと）・
トライアウト（監督）・退団（監督）・キャンプ（投手は投手コーチ、野手は野手コーチ）。
受け持つ席が空いていれば「自分で」に戻る（`effectiveStaffModes`）。

⚠ **人事はキャンプの間と年度更新のときだけ**。人の球団はキャンプの間に解任・雇用・入れ替えが
できる（`staff` 命令）。その年に就けた人を外すのは取り消しで、解任に数えない。同じキャンプで
外した監督を同じ席に呼び戻したときも取り消し（解任の数と在任年数を戻す）。CPU球団は年度更新で
球団の期待（`fronts`）と成績から入れ替わる。引退した選手の一部は指導者になって市場に出る。
契約更改の**コーチ打診**（`coachOffers`。投手コーチ・野手コーチに各1人まで）で選んだ選手は、その場で名簿を離れ
（トライアウトの受験者にはならない）、指導者の `status: 'reserved'` と行き先 `joins`（`team`・`role`・`year`）を持つ。
年度更新で終わった年の成績を席の人に足した後、市場の人数を整える前に席に就き（`seatReserved`）、前任は市場へ戻る。
年数と成績の行（「元投手（川崎で4年）」）はこのリーグの記録から数える（`careerSummaryOf`）。
契約更改の**指導者の異動**（`staffMoves`。先方要望 2026-11-23）で、監督の退任（`manager: 'leave'`）・
コーチの監督への昇格（`manager: 'pitching' | 'batting'`）・コーチの退任（`pitching|batting: 'leave'`）も決められる。
締め切りで `coaches.moves[球団]`（役職 → `{ to, id }`。決めたときの人の id と組）に控え、年度更新で
コーチ打診の席に就ける（`seatReserved`）**前に**動かす（`applyStaffMoves`）。だから「選手を投手コーチに打診 →
投手コーチを監督に昇格 → 監督は退任」が1回の契約更改で組める。決めた後に勇退・辞任で席を離れた人は動かさず、
上げるコーチが居なくなっていれば監督も続投。退任は解任に数えない（出来事は `resign` に `stepDown: true`、
文は「退任」）。異動で空いた席は `coaches.refill[球団]` に控え、すぐ後のキャンプの間に人が市場から呼ばなければ、キャンプの終わり（`fillVacancies`）に CPU 球団と同じ選び方で市場から埋める（内部昇格・まれな空席は無し。解任で空けた席は埋めない）。指導者の画面の
「年度更新で動く人事」（`staff.scheduled`。`scheduledStaffLines`）に、控えた異動と打診が出る。

⚠ **キャンプの案はコーチだけ**。コーチの居ない側の選手を監督で埋めない（「おすすめ」で練習する）。
画面に「誰の案か」（`phase.planBy`）を出す。

### ストーブリーグ

日曜に行う。2つの方式を持つ。

**1. オークション**

複数人が入札し、時間内の最高額が落札。

**2. 個人間トレード（交渉制）**

```
提示側: 欲しい選手を指定 ＋ 出す選手・金銭相当を提示
  ↓
相手が時間内に了承            → 成立
相手が条件を変えて再提示      → さらに双方の了承が必要
```

不成立になる条件:

- 時間内に成立しなかった
- 目当ての選手が**先に他で決まった**
- **資金が足りなくなった**（他の取引で使った等）

⚠ 再提示があるので、単純な「提案→承諾」ではなく**交渉の往復**になる。
どちらが最後に了承したかを記録し、条件が変わるたびに同意をやり直す。

⚠ `README.md` に「トレードは対象外」とあるとおり、これも未実装。

その後、PCは専用の表（`LineupBoard.jsx`・`PitchingBoard.jsx`）に置き換えた。
携帯は横に長い移植画面だと縦向きで守備と控えが触れないので、打順・守備・控えを
**2回のタップで入れ替える縦の表**（`src/online/TapLineup.jsx`、中身は `tapLineup.js`）に
した。1回目に押したもの（名前＝打順、守備位置の札＝守備、控え＝交代）で中身が決まり、
2回目に相手を押す。入れ替えの関数と守れない位置の判定はPCのスタメン設定と同じ。
携帯の投手起用はしばらく移植画面のままだったが、2026-11-24 にPCと同じ表（`PitchingBoard.jsx`）へ
置き換えた（`MobilePitching.jsx`。「投手起用を開く（横向き推奨）」から開く）。

### 開幕前の名簿は「初期メンバーセット」から選ぶ

開幕前の手続きは**20セットから1つ選ぶ**形にした（`src/online/rosterPack.js`・
`src/online/PackSelect.jsx`・フェーズ名 `pack_select`）。以前の初期編成
（360人の希望リスト）は置き換えて、コードから消した。

1セットは**24人**。**構成の型と格付けの型の組み合わせがセットごとに違う**
（版2。`PACK_STYLE`）。固定だと悩みどころが無い、という指摘で変えた：

| 構成の型 | 投手 | 捕手 | 内野 | 外野 | 二刀流（投／野） |
|---|---|---|---|---|---|
| 標準 | 11 | 2 | 5 | 4 | 1／1 |
| 投手厚め | 12 | 2 | 5 | 4 | 1／0 |
| 野手厚め | 9 | 2 | 6 | 5 | 1／1 |
| 二刀流 | 9 | 2 | 5 | 4 | 2／2 |
| 捕手3人 | 10 | 3 | 5 | 4 | 1／1 |

⚠ **どの型も捕手2・内野5・外野4以上**にする（どのまとまりにも控えが1人居る）。
控えの居ないまとまりのレギュラーは疲れても休めない（`restTiredFielders` は、守備を
組み直してもどの守備も適性60以上で組めるときだけ休ませる。疲労120以上は別）。外野3人の型を作ったら、通年の検査で中堅手が疲労471まで
積み上がった。厚みの違いは投手と野手の人数の差で出す。

| 格付けの型 | A | B | C |
|---|---|---|---|
| バランス | 2 | 10 | 12 |
| 少数精鋭 | 4 | 6 | 14 |
| 粒ぞろい | 0 | 14 | 10 |
| 大黒柱 | 1 | 12 | 11 |
| 主力3人 | 3 | 8 | 13 |

年齢は版3から19〜32歳（`PACK_AGE_WEIGHTS`。伸び盛りの19〜24歳を厚くし、26歳以上は尾を引く形。版2までは19〜24歳）。
画面の説明の年齢の幅は、並んでいるセットの中身から数える（`packAgeRange`）。25通りを並べ替えて先頭の20通りを使う。格は24の枠へ**ランダムに**
置く（Aが投手に固まるセットも野手に固まるセットもある）。

⚠ **どのセットを選んでも不利にならないようにする**。選ぶ時点では中身しか
見えないので、合計の力がばらつくと「当たりのセット」を引いたかで勝負が決まる。
- 格の点（A=3・B=2・C=1）の合計を全部の型で38にし、段差を**等間隔**にする
  （`PACK_RANK_SHIFT_V2` A=+8・B=0・C=−8）。等間隔なら点の合計が同じ型は
  平均の段差も同じになる。
- **8つの守備位置をどのセットにも1人ずつ置く**。くじで決めると遊撃手や中堅手の
  居ないセットができ、開幕前の打順作りが選手を勝手にコンバートする。
- **内野の控えは遊撃手か三塁手**（外野の控えはどこでもよい）。疲れたレギュラーの代役は
  その位置の適性60以上の控えだけで、一塁手・二塁手の控えは三塁や遊撃をほとんど守れない。
  遊撃手は二塁・三塁、三塁手は一塁・遊撃を守れる。一塁は控えの捕手も守れる。
- 枠の種類（守備位置×二刀流か×格）ごとに全セットぶんを少し多めに作って両端を
  落とし、**その種類の平均からの上振れの合計**が一番低いセットへ強い順に配る。
  構成が違うセットは合計の点では比べられない（投手と野手で物差しが違う）ので、
  同じ枠の平均との差で揃える。振れ幅の大きい種類から配ると開きは1%前後
  （後に回すと2.4%残った）。

⚠ **途中参加でセットを待っている人のセットは種から作り直す**ので、配ったときの
版を `member.packStyle` に残す（無い人は版1。保存の版8の移行で1を入れる）。
版1の作り方（全セットが投手11・捕手2・内野5・外野4・二刀流1＋1、A2・B10・C12。
`generateFixedPacks`）は消さずに残してある。

⚠ **格付けの段差は `RANK_LEVEL_SHIFT` を流用しない**。あれはA=0・B=-8・C=-16 で
**チームの格をチーム全体に当てる**表なので、選手の格に当てると能力が全体に
下がり、表示がほぼ全員Fになった。中心をBに置く別の段差を使う
（`PACK_RANK_SHIFT`）。投手の制球の平均で、流用すると43前後・正しい段差で49前後。

⚠ （版1）**格付けを枠の順に配らない**。構成は投手から並んでいるので、順に配ると
Aの2人がどちらも投手になり、**野手にAが1人も居ない**セットができた（実測）。
少ない格から等間隔に置いて24枠へ散らす（`spreadRanks`）。

⚠ **配ったら打順と投手起用まで作ること**（`refreshTeamPlan`）。名簿を渡すだけでは
試合が組めない。付け忘れたときは打順が空のまま開幕し、打順の入れ替えが例外で
落ちた（実測）。

⚠ **同じセットは1球団だけ**。選手のidと名前が重複すると、記録がどちらの選手の
ものか分からなくなる。取り合いになったら**球団名の順**で決める（乱数で決めると
同じやり直しで違う結果になって再現しなくなる）。選ばなかった球団には残りを順に配る。

⚠ **配り終えたらセットを捨てる**（`delete league.packs`）。20×24＝480人ぶんを
保存に抱えたままにしない。

シーズンが終わってからの流れは、契約更改（解雇する選手を選ぶ）→ トライアウト
（解雇された選手＋新たに独立リーグを目指す選手から選ぶ）→ キャンプ → 新シーズン。
開幕前のセット選択はこの1回だけで、2年目以降はトライアウトが名簿を埋める。

⚠ **年末のトライアウトの候補は12球団で実測120人**。初回だけ `teamCount * 30` を
生成していたが、オンラインに初回トライアウトは無くなったので、常に実在プール
（高卒・大学4年・FA）から引く。空の名簿を12球団ぶん埋めるには足りないので、
名簿が空の状態でトライアウトを開かないこと。

**トライアウトの画面は作り直した**（`src/online/TryoutPlanner.jsx`）。

⚠ **いまの形（2026-11-15 先方指摘で改め）**: 候補から「交渉」で**20人まで**選ぶ（`TRYOUT_WISH_MAX`）。提出は
`{ count, rankedIds, total }`（`total` は獲得する人数＝入団枠。無ければ標準の26人まで（`ROSTER_STANDARD`。
CPU球団は `autoRosterTarget` の26〜27人）。空き枠（上限28人まで）を超える値は弾かず空き枠に切る）。入団枠と指名の順位は別で、交渉の上から取り、取られたら下が繰り上がる。
**`total` を決めた案は交渉した選手だけを取る**（取り切れなければ枠が余る。選んでいない選手は入らない。
`fillsAutomatically`）。`total` の無い案（標準案・CPU・指導者に任せた案・`total` を送らない古い提出）だけ、残りを監督の判断で自動に埋める。
⚠ **`total` をいつも送っていた古い画面（Web・アプリ）の提出は、いまは「交渉した選手だけ」として読まれる**。
以前は交渉が尽きたら自動で埋めていたので、そのような提出は前より少ない人数しか取らないことがある（前と同じ動きにはならない）。
最低限（投1・捕1・野8）に届かないぶんは人数を超えて補う（交渉した選手にその位置の人が居ればその人から）。
結果は `league.tryoutResults[userId]`（ビュー `lastTryout`）。**下の段落は作り直す前の形**
（候補全員に順位・目標構成で飛ばす・誰も取り除かない）の記録で、いまは当てはまらない。

⚠ **こちらは移植できない。** 一人用は「順番が回ってきたら1人選ぶ」生のドラフトで、
オンラインは非同期なので「希望リストを1回出す」。画面の中身以前に操作の型が違う。

候補は1本のリストで扱える数ではない（開幕前の初期編成だった頃は実測360人、
年末のトライアウトは12球団で120人）。既定案は候補全員に順位を付けた状態で、
以前はそれを1本のリストにして ↑↓ で並べ替えさせていた。
300番目を1番に上げるには299回押すことになる。
作り直した画面は、左に獲得予定（並べ替える）、右に候補（守備位置・並べ替え・
名前で絞って指名する）を置く。

⚠ **`rankedIds` からは誰も取り除かない**。サーバーは上から見て空いている人を
取るので、全員残しておくと競合したとき繰り上がる。「控えへ」は末尾送りにする。

⚠ **希望順だけで取らないこと**（`ROSTER_TARGETS`）。候補の38%が投手なので、
順番どおりに取ると自分の番が回る頃には投手ばかりが残る。実測で、人の球団だけ
**投手15人・野手9人**（控えゼロ）になり、CPUは全球団が投手10・野手14で
揃っていた。野手9人では代打も守備固めも出せず、レギュラーが全試合に出続けるので、
成績の出方が一人用と別物になる。目標（投10・捕2・内6・外6）を満たした区分は
飛ばして次の希望へ進む。画面の「獲得予定」も**同じ関数**で出すこと
（`plannedPicks`）。片方だけ直すと、並んでいる顔ぶれと実際に取る顔ぶれが食い違う。

1〜3で「遊べる最小形」。4と5で深くなる。

⚠ **段階1が土台。** これが無いと1人でも遊べない（現行は2人必須）。

## 進め方の制約

### 既存のリーグは作り直しになる

参加者モデルを変えるとリーグデータの形式が変わる。
`assertLeagueVersion` が `schema` と `engineVersion` を照合して古い形式を拒否するので、
**既存のリーグは消して作り直す**。

### main に入れた瞬間に公開される

`main` は本番へ自動デプロイされる。作りかけを main に入れると遊べなくなる。

**ブランチで進め、完成してから一度に main へ入れる。**
Vercel の Preview URL を使えば、本番を止めずに確認できる。

### 影響範囲（実測）

`members` が流れている箇所:

- サーバー9ファイル（`leagueEngine` / `leagueService` / `projection` / `http` /
  `lineupCommand` / `production` / `dev` / `archiveIndex` / `storage/supabaseStore`）
- 画面3ファイル（`LeaguePanels` / `PlayerPerformance` / `TeamRoster`）
- ハーネスの検査10本以上

**検査が10本以上あるのは有利。** 壊したらそこで止まる。
